# 构建与版本规范（agent 必须遵守）

## 开发阶段

- 所有可交付开发产物只写入仓库 `artifacts/dev/`；日常预览固定 `slot-a` / `slot-b`，原生中间产物也放在该目录。`src/tests` 下的 `bin/obj` 是编译缓存，不是交付包。
- 默认使用 `Start-DevLauncher.ps1 -BuildOnly` 或开发监视器。需要 ZIP/覆盖更新包时使用 `Publish-Release.ps1 -Development -Version 0.0.0-dev.<UTC时间戳>`，可加 `-HotUpdate`；时间戳格式 `yyyyMMddHHmmss`。
- 开发迭代不递增正式版本，不创建正式标签、Release 或 `release-v*.md`。CI 也只生成 dev 包。
- 开发包反馈需注明目录、源码提交及未提交改动、构建时间、验证范围；测试通过或 agent 自测不等于用户手动验收。

## 正式版本门槛

1. 用户手动验收当前开发包，并明确表示通过。
2. 用户针对本次已验收改动明确下令构建正式版。仅说“继续”“构建给我看看”或历史发布授权均不满足条件。
3. 两项均满足后才分配版本、编写发行说明、使用 `-ReleaseApproved` 构建。这个参数是操作者声明，不替代用户授权，agent 禁止自行认定验收通过。
4. 验收后若修改产品代码，须重新提供开发包验收；不要把新改动混入已验收版本。
5. 提交、推送、打标签、上传发布仍须用户明确授权；仅授权构建不等于授权公开发布。授权仅限本次版本。

## 版本与目录

- 正式版本严格使用 `MAJOR.MINOR.PATCH`，标签 `vMAJOR.MINOR.PATCH`，包名 `BqtjLauncher-vMAJOR.MINOR.PATCH-win-x86.zip`，固定输出 `artifacts/release/`。
- 修复及小幅改进递增 PATCH；较大功能增量经用户确定后递增 MINOR 并清零 PATCH；不兼容的大改才递增 MAJOR。不要根据构建次数递增。
- 正式版本序列仅以 GitHub 远程正式 Release 为准。本地历史编号已废除，不占用版本号。每次分配前核对远程 Release 与标签，已存在远程标签先调查，不覆盖或移动。
- 开发包统一 `0.0.0-dev.<时间戳>`，不占用正式序列。历史本地包仅作开发证据，不作为正式版本基线。
- 正式包同名文件或目录已存在时停止；若是已废除的本地历史编号，经本次清理授权删除旧产物后再构建，远程已公开版本仍禁止覆盖。发布失败先调查，不借换版本号掩盖失败。
- `-HotUpdate` 仅表示包结构，不能绕过开发目录或正式版门槛。

## 清理

仅清理明确生成的编译缓存、过期开发槽位和诊断临时产物。保留当前验收包、正式交付包、源码和诊断源码；不读取或删除账号库、Cookie、日志、证书。删除前确认绝对路径在仓库内，跳过运行中产物、重解析点及疑似用户数据。不得用 `git clean` 或 `reset --hard`。
